# Knowledge base: UU (Uppsala) uppsala-data -> NOMAD upload pipeline

Notes collected while adapting `upload_UU_DFT+MC` to the new uppsala-data
layout. See `README.md` for usage, `AI_cif_inclusion_intent.md` (gitignored,
local) for the cif-intent discussion.

## Data source and naming

- Data repo: https://github.com/MaMMoS-project/uppsala-data — clone into this
  folder as `uppsala-data/` (gitignored). Datasets live in `data/<name>/`.
- Folder-name convention (uppsala-data README): reduced chemical formula with
  optional `_comment` suffix (`Nd2Fe14B`, `Nd1.5Ce0.5Fe14B`,
  `Fe16N2_exp_str`). Our output file names keep the full folder name
  (`<name>.h5`, `<name>.archive.yaml`, `uploads/<name>_archive.zip`,
  `short_name: UU-<name>`); only `chemical_formula` strips the suffix
  (`chemical_formula_from_name()` in `packages/nomad_archive_extras.py`).
- Per-dataset layout is enforced by `uppsala-data/dataset-schema.yaml`:
  `metadata.yaml`, `intrinsic_properties.yaml`, `structure.cif`,
  `RSPt/{common_input, gs_x, gs_y?, gs_z, Jij}`, `UppASD/MC_1 (+MC_2, MC_3?)`.
  Validation: `mammos-parser uppsala-data validate-dataset <dir>` (CLI in the
  pixi env) plus our internal `check_uppsala_structure()`; both run in the
  runner and hard-fail on invalid datasets.

## Derived (mammos) files — what they are

- `intrinsic_properties.yaml` ("mammos yaml v2"): `Js` (T),
  `Ms` (kA/m), `Ku` (MJ/m^3), `Tc` (K), each with `ontology_label`,
  `ontology_iri` (EMMO / MaMMoS magnetic-materials ontology, w3id.org),
  `unit`, `description`. Generated by `mammos-parser ... generate-derived-files`.
- `UppASD/MC_*/thermal.csv` ("mammos csv v3"): multi-row header (comments,
  ontology labels, descriptions, IRIs, units, short names) then data columns
  `T, Ms, Js, E, Cv, chi, U_L`. Parsed by `read_thermal_csv()`
  (`packages/data_tests_functions.py`) — note `np.loadtxt` alone fails on the
  header.
- Library roles: `mammos-parser` validates/generates; `mammos-entity` is the
  data model (Entity/EntityCollection with ontology metadata) + file I/O
  (`from_yaml`/`from_csv`/`from_hdf5`); it reaches our env transitively via
  `mammos-parser` (`mammos-entity>=0.13.0`). `to-nomad`
  (MaMMoS-project/to-nomad) turns such files into NOMAD archives.

## Archive generation (what the runner writes)

- Quantities use the **mammos-entity names/labels/units as-is**: `Js`, `Ku`
  (MJ/m^3 — no unit conversion), `Tc`, `Ms`, plus `Js_300` (Js interpolated at
  300 K from `MC_1/thermal.csv`). Earlier versions mapped `Ku` -> `K1_300`
  (labelled "Magnetocrystalline anisotropy constant at 300 K", MJ->J
  conversion) — that was wrong and is documented as changed in README.
- A repeating `mammos_entities` subsection records per quantity:
  name/value_key (identical, ME name as-is), source_type, ontology_label,
  ontology_iri, unit, description. Quantity and entry descriptions are filled
  at runtime from the ME yaml / ontology, not hardcoded.
- Entry `name` = `UU-DFT+MC-<folder>`, `short_name` = `UU-<folder>`.
- Schema base sections: plain `nomad.datamodel.data.EntryData` +
  `nomad.datamodel.metainfo.basesections.HDF5Normalizer` — **no ELN
  `Chemical` base** (unlike the original UU template and IFW), so the new
  NOMAD UI (2.0) shows `datetime`/`chemical_formula`/etc. read-only instead
  of as editable input fields; `chemical_formula` is declared as our own
  quantity and filled from the folder name when `--cif off`.
- h5 linking: the section declares a `data_file: str` quantity set to
  `<name>.h5` — REQUIRED, because NOMAD's `HDF5Normalizer.normalize()`
  (nomad/datamodel/metainfo/basesections/v1.py) opens any *string* quantity
  whose value matches `*.h5` as `<upload>/raw/<value>`; if the quantity is
  not declared in the section, the value is dropped at parse time and no
  mapping happens (observed as "no value" for all h5-linked quantities on a
  Fe12Co4N2 upload). Every quantity present in the h5 `results` group gets
  `m_annotations: {hdf5: {path: /results/<name>}}` and no inline value
  (filled server-side by HDF5Normalizer — same mechanism as to-nomad's
  `hdf_reference_mode`). Quantities not in the h5 (e.g. `Js_300` for new
  datasets) are written inline. See `h5_results_map()` in
  `packages/nomad_archive_extras.py` (old-layout aliases: Js→Js_0,
  Ku→K1_300, Js_300→Js_300).
- The `.h5` is now a genuine **mammos-entity collection file**: for the new
  uppsala-data layout, `convert_UU_data_to_h5.py` builds one
  `EntityCollection` via `dataset_collection()` (`packages/nomad_archive_extras.py`)
  — sub-collections `intrinsic_properties` (from `intrinsic_properties.yaml`
  via `me.from_yaml`), one `thermal_MC_<n>` per `UppASD/MC_*/thermal.csv`
  (via `me.from_csv`), and `raw_data` (full folder tree, plain datasets) —
  and writes it with `collection.to_hdf5(h5f, name=None)` into the h5py file
  that already carries the H5MD/creator attrs. Verified: `me.from_hdf5()`
  reads it back as nested EntityCollections with full `Entity` leaves
  (ontology_label/ontology_iri/unit/description attrs, EMMO IRIs); the
  NOMAD h5-linking annotations point at the new paths
  (`/intrinsic_properties/Js`, …; old-layout h5 files still map via
  `/results/...` aliases). Old GS/Jij/MC layout keeps the hand-written
  `/results/` h5.

## cif / structure preview (optional, default OFF)

- `--cif off` (default): no structure embedded in the yaml; `chemical_formula`
  (own quantity, from the folder name) populates the Material section.
- `--cif auto/on`: `structure.cif` parsed locally with ASE -> inline
  top-level `run` section + `metadata: {domain: dft}` (OptimadeNormalizer
  renders the 3-D preview server-side); `chemical_formula` omitted then.
- Independently of `--cif`, the `.cif` is **always** shipped in the zip when
  present: as `cif_structure_<name>.cif` at the zip root and under
  `datasets/<name>/structure.cif` (raw data / provenance). `--cif` only
  changes the `.archive.yaml`. With the run section embedded,
  `chemical_formula` MUST be omitted — otherwise the server-side
  ResultsNormalizer fails with "Could not populate compositional data as
  'elements' is already defined" (observed on a Fe12Co4N2 upload
  2026-11-17). NOMAD never reads the cif at upload time; the preview is
  static (regenerate the archive if the cif changes). `ElnWithStructureFile`
  is deliberately not used (broken on nomad-lab 2.0.0, see
  to-nomad branch `feature/subcollection-subsections`).

## Environment / libraries

pixi env `upload-uu-dft-mc`: h5py, pandas, pyyaml, ase, scipy, matplotlib,
ipykernel (conda) + mammos-parser (pypi; brings mammos-entity/units/analysis).
All are still used: h5py/pandas/pyyaml/ase in the pipeline; scipy/matplotlib/
ipykernel only for the old GS/Jij/MC layout and the evaluation notebook;
mammos-parser for validation + ontology metadata. `requests`/`pint`/
`nomad-lab` remain commented out. `mammos-entity` is used directly in code
but declared only transitively — consider adding it explicitly.
